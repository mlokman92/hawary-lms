# Internationalisation (web)

The back-office and the learner tree both ship in **English (default)** and
**Bahasa Melayu**. This note records how it is wired and what to do when you add
a screen.

## Why a hand-rolled dictionary and not i18next

The app is a single Vite bundle with no SSR, no runtime locale negotiation and
no need for ICU message syntax. What it does need is that a Malay translation
can never silently go missing. A typed dictionary gives exactly that: the key
union is `keyof typeof en`, so a typo in `t('…')` is a compile error and a
missing Malay entry fails `tsc`. i18next would have added a dependency, a
loader, and stringly-typed keys to get less.

## Shape

```
apps/web/src/lib/i18n/
  index.tsx            LanguageProvider · useT() · translate() · getLang()
  dict.ts              composes the namespaces into `en` / `ms`; exports TKey
  locales/en/<ns>.ts   English copy — the source of truth
  locales/ms/<ns>.ts   Malay copy, typed against its English sibling
```

Keys are **flat and self-prefixed** — `'students.filter.all_statuses'`, not
nested objects. That keeps `TKey` a plain union of string literals, so
autocomplete works and no dotted-path type machinery is needed.

Completeness is enforced twice:

- each `ms/<ns>.ts` is annotated with the `<Ns>Dict` type its English sibling
  exports, so a missing, extra or misspelled key fails in that file;
- `ms` in `dict.ts` is annotated `Record<TKey, string>`, so a namespace wired
  into `en` but forgotten in `ms` also fails.

One namespace per feature area. They exist so a feature's copy sits next to
that feature's work — and so parallel edits do not collide.

## Using it

```tsx
import { useT } from '@/lib/i18n'

export function StudentsPage() {
  const { t, tn } = useT()
  return (
    <>
      <h1>{t('students.title')}</h1>
      <p>{t('students.joined', { date })}</p>
      <p>{tn('students.rows', rows.length)}</p>
    </>
  )
}
```

- `t(key, vars?)` — `{name}` placeholders; an unknown placeholder is left alone
  rather than blanked, so a bad interpolation is visible instead of silent.
- `tn(base, count, vars?)` — picks `<base>_one` / `<base>_other` and injects
  `{count}`. Malay does not inflect for number, so both Malay forms are usually
  the same string; the types still require both.
- `translate(key, vars?)` — the non-reactive escape hatch for plain functions
  (`lib/format.ts`, `lib/storage.ts`). It reads a module-level mirror of the
  language that `LanguageProvider` keeps in sync. **Components must not use
  it** — it does not subscribe to language changes.

### Module-level constants

A constant built at import time cannot call a hook. Two patterns, both in use:

- **enum → label maps** store a `TKey` and resolve at render:
  `features/{students,instructors,learn}/status.ts` expose `labelKey`, and call
  sites render `{t(STATUS_META[row.status].labelKey)}`. Those three maps live in
  the `common` namespace under `status.*` because the same enum is rendered on
  unrelated surfaces.
- **lists built per render** become a function of `t`:
  `const nav = (t: TFn) => [...]` — see `components/AppSidebar.tsx`.

### Dates and money

`lib/format.ts` (`fmtDate`, `fmtDateTime`, `fmtMonthYear`, `fmtDays`) reads the
language at call time and switches between `en-MY` and `ms-MY`. Always use those
helpers rather than a bare `toLocaleDateString`.

`formatMYR` in `packages/shared` is language-neutral (RM + digits) and is left
alone.

## Where the switcher lives

- `components/UserMenu.tsx` — a **Language** submenu beside **Theme**. Both are
  per-device display preferences, and `UserMenu` is mounted by the shared
  `ShellSidebar`, so staff and learners get the same control.
- `components/LanguageToggle.tsx` — the standalone control for surfaces with no
  sidebar. Mounted in `AuthCard`, which covers sign-in, sign-up, forgot and
  reset password. The choice has to be reachable *before* sign-in.

## Persistence and detection

`localStorage['hawary.lang']`, mirroring `hawary.theme`. With nothing stored the
provider follows `navigator.languages` — a device set to Malay gets Malay
without hunting for the switcher — and falls back to English.

The provider also stamps `document.documentElement.lang`, which screen readers
and the browser's own translate prompt key off.

**Not** stored in the database. A language is a per-device display preference,
not tenant data; putting it on `profiles` would mean a round trip before first
paint and would fight the local choice on a shared machine. If per-account
sync is wanted later, add `profiles.locale` and seed the provider from it —
`LanguageProvider` already accepts a `defaultLang` prop for exactly that.

## Adding a screen

1. Add keys to `locales/en/<ns>.ts` and the matching Malay to
   `locales/ms/<ns>.ts`. Reuse `common.*` before inventing a key.
2. `const { t } = useT()` and render `t('…')`.
3. New namespace? Create both files and wire them into `dict.ts` (two imports,
   two spreads).
4. `pnpm --filter web typecheck` will tell you if the Malay side is incomplete.

Whole sentences get one key with placeholders. Do not concatenate fragments —
Malay word order differs from English and assembled sentences cannot be
translated correctly.

## Bahasa Melayu house style

Malaysian *bahasa baku*, not Indonesian. Sentence case, second person "anda".

pelajar · pengajar · kursus · modul · nota · tugasan · penilaian · markah ·
gred · invois · bayaran · baki · tertunggak · log masuk/keluar · kata laluan ·
e-mel · muat naik/turun · pautan · fail · tetapan · kemas kini · hantar ·
simpan · padam · terbitkan · draf · jemputan · pendaftaran · akademi ·
papan pemuka.

Not: siswa, kelas (for course), tugas, ujian, nilai, faktur, tagihan, sandi,
surel, unggah/unduh, tautan, berkas, pengaturan, perbarui, kirim, hapus, opsi.

Left untranslated: brand names (Hawary LMS, ToyyibPay), currency (RM/MYR),
user-entered data, enum values, and generated codes (`student_no`,
`invoice_no`). Server-side error messages from Supabase and the Edge Functions
are still English — see below.

## Known gaps

- **Server-side copy is not translated.** `ErrorBlock` renders
  `error.message` straight from Supabase/PostgREST, and the `upload-media`,
  `send-invitation` and pay-link Edge Functions return English. Client-side
  errors the app raises itself *are* translated.
- **The mobile app** (`apps/mobile`) has no i18n yet. When it is wired, the
  dictionary should move to `packages/shared` so both surfaces share it; the
  namespace layout is already the right shape for that.
- Emails (invitations, pay links) are English-only.
